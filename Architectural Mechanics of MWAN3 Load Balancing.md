In the context of your Local Multi-WAN design, the load balancing architecture relies on the OpenWrt **MWAN3** package, which fundamentally operates differently than "true" channel bonding.  
Here is a breakdown of how Multi-WAN load balancing functions in this setup:  
**MWAN3 vs. True Channel Bonding**It is critical to understand that this local architecture is **not true channel bonding** 1\. True packet-level channel bonding splits a single TCP stream (like a single file download) across multiple links and requires a remote VPN or bonding server (like Speedify or MPTCP) to reassemble the packets on the other end 2\. Because your design specifically avoids routing traffic through a remote server to prevent severe latency overhead in Lebanon, it relies on OpenWrt's MWAN3 for **session-based load balancing and policy-based routing** 1\.  
Instead of splitting a single stream, MWAN3 distributes multiple concurrent IP connections across your available internet paths (the two VDSL PPPoE sessions and the cellular LTE) 1\. While a single standard browser download will not magically double in speed, multi-threaded applications like Internet Download Manager (IDM), torrent clients, or general household traffic with multiple devices will successfully saturate the aggregate bandwidth of both WANs 3, 4\.  
**The Underlying Mechanics of MWAN3**MWAN3 acts as a control plane by manipulating the Linux kernel's networking stack:

* **Unique Gateway Metrics:** For the load balancer to work, every physical WAN interface must be assigned a unique logical gateway metric within the default routing table 5\. Without unique metrics, the Linux kernel refuses to instantiate multiple default routes, leaving secondary WANs functionally dead 5\.  
* **Packet Marking:** MWAN3 utilizes iptables (or nftables in newer OpenWrt builds) to apply specific firewall marks (fwmarks) to packets as they transit the PREROUTING chain 4, 6\.  
* **Policy Routing:** The Linux Routing Policy Database (RPDB) intercepts these marked packets and steers them into specific, dynamically generated routing tables for each WAN, dictating exactly which path the flow must take 4, 6\.

**Configuration Hierarchy**To intelligently manage traffic, MWAN3 uses a strict, four-tier hierarchical configuration 7:

1. **Interfaces & Health Tracking:** The software continuously monitors the vitality of your links by sending ICMP pings to highly reliable, geographically distributed public DNS resolvers (e.g., 1.1.1.1 or 8.8.8.8) 7\.  
2. **Members & Weighting:** A "member" assigns a mathematical weight to an interface based on its connection speed 8\. For example, if your VDSL line can handle 50 Mbps and your LTE line handles 100 Mbps, you would assign a 1:2 mathematical weight ratio 9\. This ensures the load balancer algorithmically distributes traffic symmetrically without starving the slower link 9\.  
3. **Policies:** Policies group these members together to dictate routing behavior 8\. You can set a policy for **bandwidth aggregation** (utilizing WAN1 and WAN2 simultaneously) or **strict sequential failover** (using WAN1 exclusively, and only failing over to WAN2 if ICMP pings are totally lost) 8\.  
4. **Rules:** Rules classify incoming traffic by source IP, destination IP, protocol, or port, and force it into a specific policy 9\. This allows for highly customized network steering—for example, you can write a rule stating that "gaming traffic always uses the LTE WAN" while "bulk downloads use the VDSL WAN" 10\.

**Algorithmic Failover**Because MWAN3 constantly tracks link health via ping traces, it provides seamless resiliency 7\. If someone physically unplugs the VDSL modem or the ISP drops the connection, MWAN3 detects the packet loss 11\. Within a mathematically configured timeout window (e.g., 15 seconds), traffic flow is algorithmically rerouted exclusively through the surviving cellular interface 11\. Once the VDSL feed is restored and passes the tracking window's stability checks, MWAN3 automatically restores the load-balanced aggregation policy 11\.
